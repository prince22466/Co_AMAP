# Top-p data-dependent tail attribution — planned

The first 4K control spent about 110 seconds draining 59 to 0 requests, while the second drained 64 to 0 within a single 10-second server-metric interval. The preceding top-p exponent-reuse experiment matched sampled outputs but did not improve kernel latency. The two phenomena are not yet connected.

Novel question: can the **unchanged** production top-p kernel show sufficiently large input-dependent latency to plausibly contribute to an extreme drain, despite identical vocabulary and batch shapes? Existing sampled-normal timings do not answer this. Measure the existing kernel only with a few deliberately contrasted synthetic distributions: Gaussian (previous reference), equal logits (tie stress), and a single dominant logit, at p=0.95, vocabulary 130560, batch 1 and 64. Alternate cases with warmed CUDA-event measurements, identical allocations and no concurrent server. This is a falsification screen, not a production distribution estimate or whole-serving attribution. Record both raw timings and test completion; if there is no large per-step difference, deprioritize this mechanism. If there is, obtain actual worker logits/frequency and a native timeline before concluding causality or designing changes. No production or benchmark source changes.
