# Native resource attribution for top-p — planned

The v14 trace observed `_topk_topp_kernel` in the late 4K window, but CUDA graph visibility was incomplete, so its whole-serving share remains unknown. Two distinct scratch optimizations (first-pass exponent reuse and speculative two-decision search) were rejected after limited correctness checks and no microbenchmark win. The latter was ~28–31% slower; its resource cause is unmeasured. Existing native counters in v15 were for GEMM, not this top-p kernel.

Missing evidence: for the unchanged top-p kernel, are registers, occupancy, instruction throughput, or memory traffic plausible constraints that explain why speculative search added cost? A minimal native analyzer capture will target one warmed original `_topk_topp_kernel` launch at batch 64/vocabulary 130560, top-p 0.95 and synthetic Gaussian logits. Collect launch, occupancy, speed-of-light and memory sections only, with a fixed timeout, on the idle GPU. Profiler replay perturbs timings and synthetic input is not worker attribution. If counters show no concrete new mechanism, stop this direction; do not rerun a tile sweep, claim a serving gain, or modify the installed package.

## Result and new lead

The ixkn capture completed with exit 0 for one warmed unchanged `_topk_topp_kernel` launch, synthetic Gaussian batch64/vocab130560/top-p0.95. Grid **16 blocks** x 256 threads; 193 vector registers per thread, 512 bytes shared per block; achieved occupancy **6.68%**, theoretical **12.50%**, with 0.25 waves per CU. The analyzer attributes the theoretical limit to vector registers and warns about the small grid. L2 read hit rate 96.60%, DRAM read efficiency 2.85%, LSU utilization 26.11%. Duration 3.580 ms under profiler replay. These counters are diagnostic, not serving time or causal proof. Source SHA-256 `64c66699cd398c2eafe9eb91f0e189162f83a6f83a209651048e163d7d6fcee8`; report SHA-256 `48cc5d6cbdb1f7cf3d5d64ef9a0554a0db05e6679a4cb12deb0fa12b67add024` backed up off-host.

New hypothesis: wrapper uses `min(num_compute_units, batch)` program instances, each processing multiple rows in a serial loop. A bounded `min(4 * num_compute_units, batch)` per-row program grid could fill more of the device without changing threshold math or cross-row semantics. Scratch storage must be expanded correspondingly: on this system at vocab 130560 the cap grows from 16 to 64 rows (~8 to ~32 MiB FP32); startup allocation and 16K KV capacity may suffer. This is a general resource-based scheduling/dataflow hypothesis, not an established competition-eligible implementation. Smallest test: scratch-only wrapper with original kernel, bitwise differential cases including graph replay and buffer reuse, then alternating warmed full-call timings at actual batch sizes, including allocation. Reject on mismatch, no material kernel win, or unsafe capacity/fallback; no production change unless integration, actual worker execution, correctness, matched serving and eligibility are established.
