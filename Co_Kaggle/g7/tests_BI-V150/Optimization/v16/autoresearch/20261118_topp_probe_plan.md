# Top-p exponent reuse — proposed probe

Status: **unmeasured hypothesis**, not a production candidate. Do not modify the installed package or a running server.

- Closest prior outcome: v14 late 4K worker trace observed 784.36 ms of `_topk_topp_kernel` in a roughly 10.1-second window; incomplete decode graph visibility prevents assigning the whole critical path. v15's sampler work optimized division/argmax or buffer ownership, not this top-p kernel; its provisional candidate remains under separate validation.
- Material novelty: in the standalone top-p branch, retain the FP32 exponentials produced by the existing first pass in its per-program scratch buffer, then read them in the second pass instead of reloading logits and recomputing exponentials. The existing threshold search, probability normalization, tie handling, and original logits remain unchanged. Compacting outliers into the same buffer requires explicit synchronization and proof that writes cannot clobber unread values. This adds a full-buffer write and barriers, so it may be slower.
- Missing evidence: actual production branch/frequency and contribution; exact behavior for finite near ties, tails, infinities, NaNs, mixed k/p, strides and repeated graph inputs; performance including all scratch and synchronization; rule eligibility and 16K effect. The 4K trace alone is not a whole-run gain.
- Smallest decisive test after the control finishes: make a scratch-only copy of the installed kernel, preserve the original as reference, and compare exact masks/output across representative and adversarial inputs, including tail and buffer reuse. Then alternate warmed end-to-end kernel timings at representative batch/vocabulary shapes, including the added writes and barriers. Reject on any mismatch, unsupported synchronization, or no material kernel benefit. A profiler-off matched serving comparison and production integration would be subsequent steps, not implied by a microbenchmark.

CPU audit: the model's `generation_config.json` specifies temperature 1.0 and top-p 0.95; the benchmark client does not explicitly set top-p, and the server logs report applying that model configuration. The actual worker branch/frequency still requires direct attribution.

## Completed probe — rejected for lack of a material kernel win

The full remote log and scratch source were retrieved after SSH access recovered. Exit code 0, completed 2026-11-18 16:03:59 UTC. All 13 named sampled cases passed bitwise output comparison to the installed baseline, twice each: random/top-p=1/combined top-k and top-p for batches 1x8191, 8x8193, 8x130560 and 64x130560, plus one set of sampled ties, near-ties, infinities and NaNs. These are limited direct tests; no independent mathematical reference, noncontiguous input, changing graph replay, production worker, RNG or accuracy validation was performed.

Alternating warmed CUDA-event medians, 12 samples each, vocabulary 130560 and synthetic normal logits with top-p 0.95: batch 1 baseline/candidate 0.88957/0.88366 ms (~0.7% faster); batch 8 1.04148/1.05177 ms (~1.0% slower); batch 64 3.63553/3.68174 ms (~1.3% slower). Timings include scratch writes and barriers but use synthetic logits and do not establish serving performance. Reject this particular exponent-reuse mechanism for routine continuation; reopen only with material new evidence. No integration or serving experiment was performed.
