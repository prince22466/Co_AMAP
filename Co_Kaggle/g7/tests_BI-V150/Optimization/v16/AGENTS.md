## Research loop
1. Read RESEARCH_QUEUE.md and prior v0–v15 ledgers, including open/latest v15 PRs and experiments not yet on main. Do not repeat completed profiling, shape sweeps, rejected experiments or stacks; only reopen with specific new mechanism/evidence. Log nearest prior outcome, material novelty, missing evidence, smallest decisive test, and go/no-go before allocating GPU. No generic re-profiling.
2. Rank candidates by potential 4K end-to-end time reduction, evidence and 16K risk. Use archived traces; collect only missing production attribution, especially graph-visible decode time. One reversible hypothesis at a time; use direct independent correctness tests, tails, strides, dtypes, fallback and graph replay; verify worker source and actual kernel dispatch. Never infer end-to-end gain from kernel speed alone.
3. Warm alternating kernel A/B, representative actual shapes and weighted impact; short matched profiler-off serving screens on both lengths with fresh restarts, same cache state/order/seed, including concurrency 64 and a decode-length screen when justified. Report total tok/s, requests, failures, TTFT/TPOT, prefix hits, KV capacity/preemptions, variability. Avoid extra scratch that reduces 16K capacity. Reject material regressions; do not accept any unresolved 16K drop. Default latency research guard: <=5% mean TTFT/TPOT increase in each case and competition limits; not an official threshold. Never substitute quick diagnostics for score.
4. Only promising candidates proceed to unchanged external half-runs, both lengths, profiler OFF, two repeats per case, all requests successful; fresh original-v16 control may be reused within same allocation only with identical hardware/runtime/protocol and source. Independently replicate matched A/B across server restarts; alternate order where possible. Evaluate cumulative vs original and incremental vs accepted parent; stack only individually supported candidates then retest both workloads. Numeric gate: 4K ratio >=3011.12/2817.15, 16K >=1.0. No 2% negative allowance. Human runs unchanged MATH-500 and official full runs before final acceptance. Distinguish provisional, replicated half-run, and full-run/accuracy validated.
5. Publish candidate PR/checkpoint for observable improvement even below goal, clearly provisional until replication and all gates. Revert failures; preserve negative findings and continue until verified development target or actual deadline/blocker. Do not auto-merge or claim +60% until official full-run confirms. If human elects to run half-runs manually, hand off exact source, controls, commands and evidence; do not duplicate their work.

## Time and preservation
Half-run historical duration ~90–120 minutes per two-case run; 90 min hard minimum, conservative guard initially >=150 min for one, >=275 min for two. Raise estimate if slower, reserve >=25 min for off-instance backup/PR handoff. Use confirmed operator UTC deadline, never reset within allocation. Do not run if guard refuses or source/worker identity not verified. Checkpoint on start, each valuable/rejected result, before long run and <=30 min intervals except blocking half-run (durable start and completion manifests). Commit tested source before starting server, no source changes while serving. Push source separately; helper commits evidence only. Back up raw data outside instance, no secrets. Do not kill unrelated processes. No GPU allocation or automatic agent is started by this setup.
