## Completed GEMM research — do not repeat

- v7 implemented grouped program-ID ordering, M/N edge masks instead of modulo remapping, and direct FP32 accumulation in Linear. It recorded 146 distinct production shapes, 34 paired kernel comparisons (proxy, real large/small M and forced group-1), and 58 passing direct operator tests. Use the post-experiment findings rather than the older v7 proposal's pre-test status.
- Grouping the wide BF16 (M,K,N)=(2048,2048,12288) projection reduced latency from 1405.57 to 1150.38 µs in v7 group-1/group-8 control; grouping (2048,6144,2048) regressed from 723.28 to 760.58 µs. Small-M and narrower cases were already explored, including negative/neutral results.
- v11 revisited selective grouped MM: two alternating kernel screens reduced the wide-projection median from 1.40223 to 1.16975 ms and 1.41153 to 1.17371 ms; seven focused GPU tests passed. Balanced short-serving A1/B1/B2/A2 (4K: 2464.25/2054.31/2509.82/2473.56; 16K: 3196.90/2596.40/3235.04/3194.16 tok/s) was inconclusive, with cold/warm differences; no half-run go. A second-projection grouped extension regressed 0.72554 to 0.76789 ms and was rejected. See the v11 handoff, [PR #236](https://github.com/prince22466/Co_AMAP/pull/236) and recorded candidate commit 67e4492d.
- **Decision:** close this line for routine v15 research. Do not redo grouped tile-order, GROUP_M sweeps, previously tested edge-mask/address optimizations, direct Linear accumulation, generic shape inventory, or broad proxy-shape microbenchmarks. Do not port v7/v11 changes by default: no repeatable serving benefit was established. Only a concrete new causal mechanism supported by v15 evidence may justify a narrowly scoped follow-up, not another identical experiment. Reuse tests for any genuinely changed operator; correctness and serving acceptance are not waived.
- Historical production BF16 MM families (M,K,N): (M,2048,12288), (M,2048,2560), (M,2048,2048), (M,6144,2048), with M=2048 and small M=1..256, A row-major and B strides (1,K). Linear (M,2048,130560), M=1/256. The inventory is distinct shapes, not a frequency distribution; collect only missing frequency/phase/resource attribution needed for a new experiment.

## G1 — new GEMM K-loop/dataflow and resource efficiency

Start from unchanged v15 MM/Linear implementation and existing tuning configuration. Identify which actual production shape/phase and tile are limited by tensor-core issue, load latency, memory bandwidth, register spills or shared memory. Use archived shape/timing evidence, then obtain a minimal native-profiler capture for missing counters and emitted Triton/ISA. Focus on a different mechanism than v7/v11:
- K-loop pipelining and staging of A/B tiles, vectorized/coalesced loads, resource-aware BLOCK_K and tile aspect ratios, latency hiding with measured register/shared-memory tradeoffs. No generic blind sweep; select configurations from observed bottleneck and test realistic shape weights.
- Persistent or work-partitioned GEMM only if supported and evidence identifies wave underutilization or load imbalance; include workspace/init/reduction cost. Safe FP32 split-K reduction only if needed and proven correct; do not activate existing unsafe atomic accumulation or duplicate bias.
- Preserve precision, indexing, strides, dispatch, fallback and graph replay. Compare against original v15 for the new mechanism; no grouping/edge-mask/accumulator rediscovery.

## G2 — new projection/epilogue and memory-traffic reductions

Inspect real projection chains for redundant copies, intermediate global writes/reads, layout conversions or launch overhead that could be eliminated by a genuine fused operator/epilogue or workspace-lifetime change. Prioritize only paths confirmed in v15 traces; respect bias, activation and quantization-disabled semantics, and avoid fusing across incompatible dependencies. For small-M/vocabulary Linear, investigate actual weight traffic, parallelism and output/reduction overhead if profiler evidence warrants; do not repeat v7 small-M grouping or direct-dot experiments. Preserve original selection/fallback; include complete operator chain cost, graph capture/replay, scratch and impact on 16K KV capacity. Prefer solutions that free rather than consume persistent memory. Test direct references with ragged M/N/K, alternate strides, BF16/FP16, mm.out, bias, and fallback as relevant.

## Existing capacity and queue accounting — reuse, do not rediscover

- [v5 findings](../../../profiling/v5/v5_decode_16k_bottleneck_findings.md) already derive 42 layers × 2 KV heads × 128 × K/V × 2 BF16 bytes = 43,008 bytes per logical token (42 KiB), and 64 full 16K prompts require 42 GiB before decode, ~44.63 GiB including 1024 generated tokens. This exceeds the 32 GiB BI-V150. No expectation that small memory savings will admit all 64 full contexts.
- Both v14 [telemetry server log](../../../v14_profile_runs/20261115_161906_1085_telemetry/server.log) and [trace server log](../../../v14_profile_runs/20261115_172508_8779_trace/server.log) already report 521,840 allocated KV tokens, 3.98x concurrency at max length 131072. At the recorded model geometry this is ~20.90 GiB logical KV storage; if block size 16 as previously observed, 32,615 blocks. Approximately 31 full 16K prefixes or 29 full 17,408-token contexts fit without sharing (not an instantaneous scheduling limit). One GiB of genuinely reclaimable memory buys ~24,966 logical tokens before block rounding, about 1.4 full 17,408-token contexts; realized gain depends on allocation and scheduling.
- The v14 [telemetry analysis](../../../v14_profile_runs/20261115_161906_1085_telemetry/analysis.json) already contains before/after metric deltas: zero local/external prefix hits and cached prompt tokens in both diagnostic workloads; queue-time sum/count 960.83 s/256 (4K, ~3.75 s/request) and 31,369.85 s/128 (16K, ~245.08 s/request); four new 16K preemptions, zero new 4K. The counters are summed request times, not an end-to-end critical-path or removable queue-time estimate. Use the before/after snapshots for exact totals rather than final periodic sample.
- Therefore skip another baseline capacity/queue/prefix-hit survey, generic scheduler/CPU-GPU idle profiling, and rechecking the old cache-write tiling. Missing evidence is **which specific live or redundant allocations consume non-KV budget, whether savings survive peak/graph capture, and whether a new change actually creates usable blocks or reduces recomputation**. Existing Stage 2 directory has instrumented source but no measured result in the tracked archive; reuse instrumentation if applicable, not an automatic rerun of every Stage 2 probe.

## K1 — allocation-lifetime attribution and real non-KV savings, highest KV priority

Start at vllm-plugin-FL/vllm_fl/worker/worker.py (MemorySnapshot, memory_profiling_fl, WorkerFL.determine_available_memory), worker/model_runner.py (persistent buffers, KV initialization, graph capture), compilation/graph.py and actual allocator/API paths. Scheduler_fl.py extends AsyncScheduler for structured output, not a proven KV allocator. Read installed upstream allocator/scheduler for diagnosis only. Reuse the existing model geometry, capacity and serving telemetry above; check only changed runtime/configuration or missing physical layout/padding evidence. Attribute the *unexplained non-KV budget* to weights, peak activations, static buffers, allocator reserved vs allocated, graph pools and non-torch memory using existing startup logs first; acquire a targeted allocation/lifetime trace only where needed to establish a reclaimable candidate. Separate reclaimable temporary allocations from live buffers. The current worker computes requested memory minus profiled non-KV memory and the graph estimate when enabled; actual graph capture follows KV allocation. Verify the runtime platform/estimate path and reconcile measured peaks; do not toggle graph estimation, increase returned bytes or subtract hypothetical savings.

Try lifetime shortening, eliminate duplicate buffers/copies, safe workspace reuse, memory-efficient operator fusion, and graph-safe allocation reuse where real savings exist. Only count additional blocks when actual allocation changes at identical flags and normal memory accounting. Verify address stability and alias/lifetime safety across asynchronous streams and graph replay; stress maximum supported contexts within allocated capacity, mixed batches, repeated startup/replay, no OOM or token loss. Report actual block delta, not theoretical free VRAM. If no real reclaimable memory exists, stop this line rather than overriding safety.

## K2 — block utilization and recomputation accounting

Reuse the measured queue, prefix-hit and preemption counts. Quantify only the missing block-level cause (e.g. live vs free/cached refs, internal fragmentation, duplicate allocation or actual recompute tokens) if K1 or a source audit identifies a plausible exact remedy. Do not collect a second generic scheduler/queue telemetry dataset. Distinguish active references from cached/free blocks. Estimate useful capacity bound given bytes per token and measured live context. If avoidable duplicate allocations or copies exist, implement a general exact fix inside v15-owned storage/operator path. Prove identical logical KV for shuffled pages, tail, shared prefixes, cancellation, preemption/resume, interleaved requests, and cache isolation; check block-table/slot mapping and graph capture. No change to block size, admission policy, cache dtype, prefix-cache policy or token retention. Pure scheduler/allocator policy experiments with ambiguous eligibility are diagnostic-only until organizer approval. No direct merge of upstream code.

## Out of scope for routine v15 research

No generic KV write/read optimization, standalone RMSNorm fusion, attention tile/stage/page-index research, sparse attention, operator-dispatch swaps, or scheduler-policy changes. A genuinely new projection fusion or storage-lifetime improvement may touch an existing path only if it removes different measured work, preserves current semantics and passes the novelty and compliance gates. Do not revisit old implementations just because they are absent from v15.

## Experiment order

First cycle: review archived v0–v14 evidence on CPU; identify the highest-value missing GEMM resource attribution or specific reclaimable allocation. Run only its smallest decisive probe; then select the best justified G1/G2/K1/K2 candidate. No mandatory G1 and K1 pair, no historical-candidate integration or baseline profiling campaign. Use serial GPU tests, independently reversible diffs and short serving screens. Re-rank using frequency-weighted kernel savings, measured capacity/recompute savings, actual serving impact and risk. Test stack only after individual contributions are established. Stop spending on hypotheses without measurable causal evidence; preserve negative results.
